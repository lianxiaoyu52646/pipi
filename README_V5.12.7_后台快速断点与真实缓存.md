# 皮皮 V5.12.7｜后台缓存稳定与性能优化

## 适用版本
- 增量包只适用于完整升级到 **V5.12.6** 的 Android Studio 工程，保留其20本离线原著、7套词书、小毛娃娃头像和生词本/FSRS。
- 原来的 Android 包名仍为 `com.sprint7.offline`。版本号升级到 5.12.7 / versionCode 36。
- 完整工程依然**不提供**本机独立许可的大型 Kokoro / Piper 模型和 sherpa AAR。沿用原工程语音资源；升级请使用相同签名证书、不要卸载或清除 App 数据。

## 代码中已经实现
1. 新建 `VoiceCacheIndex.kt`：SQLite 持久化的逐句发生位置队列；按 **音色、语速、实际离线语音目录内容摘要**区分任务。数据结构含片段文本、文件缓存键、章节及核验状态。
2. 旧版 PCM 原封不动保留：升级后首次缓存执行**一次全量文件校验/建立索引**；当语音目录、音色、语速未变时，此后的恢复只查询下一条未完成索引，不再每次全量扫描8.3万段音频。原著目录内容变化会自动重新建立索引，但仍复用兼容PCM。
3. 同一句话在多章出现时，一份PCM即可一次性更新所有对应位置的进度（SQLite事务），避免统计误差。
4. 新音频必须**先写盘和校验成功，再提交数据库完成记录**。如果合成完成但数据库提交前进程崩溃，下次能直接识别已有PCM并补记，不重复合成。
5. 总任务结束前对已完成文件进行一次独立核验，发现丢失或损坏的PCM会重新入队补齐；缓存索引损坏会自动仅重建索引，原音频不删除。
6. Android原有独立前台服务、PARTIAL_WAKE_LOCK、看门狗终止原生卡死的独立进程、恢复闹钟与自动重试机制全部保留。
7. 服务重新启动时先展示前次持久化进度，不再默认归0。首次导入期间显示独立索引校验数；页面不把扫描动画冒充真正生成。
8. 复习端、书籍内容、音频格式和朗读缓存键未改；20本书当前有 **82,926个句段位置、81,562个不同缓存键**。

## 速度改善范围
加速的是**续接/重试/恢复准备阶段**（用数据库定位缺失片段代替每次重新遍历全量文件）。Kokoro 原生模型单句合成速度并未承诺固定倍率；仍沿用已有按CPU选择2~4线程、长句切分与单模型执行，以控制内存和发热。首次索引可能消耗明显时间；20本全部生成仍需要较长时间和足够空间。

## 安装方式
1. 备份 V5.12.6 工程和当前 Android App 数据。
2. 增量ZIP**按原目录结构解压到工程根目录**，例如覆盖 `app/src/main/...` 和 `app/build.gradle`，不要只解压单个 Kotlin 文件。
3. 用 Android Studio 或现有 Windows 构建脚本重新编译；确认本地模型及 AAR 存在。
4. 使用同一应用ID、**同一签名证书**安装覆盖旧版APK，**不要卸载**。新数据库自动创建并导入既有语音缓存。
5. 缓存期间不建议对 App 开启极限省电或强行停止；锁屏、正常切后台仍由前台服务负责运行。

## 验收和局限
- 代码测试：23/23 JS 回归通过，20本全文/语音索引、7套词书、256词典分片静态校验通过；模拟 SQLite 已检查中断/重复键/恢复/损坏文件修复；Kotlin 核心文件使用接口桩编译通过；4种屏幕宽度缓存页测试通过。
- 尚未在完整 Android SDK + Kokoro 模型真实编译 APK；尚未在你的机型锁屏运行72小时。因此不可声称已被证明“几天绝不中断”。Android 厂商的后台限制、过热和强行停止依然可能阻止立即重启，程序尽力恢复并保留工作成果。
- 用户主动点「暂停」会停止任务；进程被系统杀掉，恢复需要系统允许启动前台服务或用户重新打开App。系统层禁止后台启动时无法软件保证零延迟。

## 复核日志建议
Windows命令行：`adb logcat -s PipiVoiceCache PipiCacheRecovery`，观察 `synth begin`、`watchdog`、`recovery` 与SQLite索引恢复事件。页面以“完成数、真实新增数、最后写入时间、速度、自动恢复次数”为准，不以动画为准。
